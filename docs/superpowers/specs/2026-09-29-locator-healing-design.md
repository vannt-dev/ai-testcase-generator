# Locator Healing — Design

Status: approved (design), pending implementation plan
Roadmap: Phase 4 of the project roadmap (README.md), step 2 of 2
Builds on: `docs/superpowers/specs/2026-09-29-playwright-automation-design.md`

## Purpose

A generated Playwright test fails because the app's markup changed: a button
was renamed, a label moved, a test id disappeared. The tester has the page
object file, the Playwright error and the page's current HTML. This step asks
Claude which locators broke and how they should read now, and it patches only
those lines. It never changes test steps or assertions. When the app's
behaviour changed rather than its markup, that may be a real bug, so the AI
says so instead of hiding it.

## Decisions

- **Input:** one page object file (`pages/X.ts`, generated by the Automation
  page and possibly edited by hand), the Playwright error output, and the
  page's current HTML or ARIA snapshot.
- **Scope:** locators only. The AI may change the strategy/value of locators
  that already exist in the file. It adds no locators and does not touch
  spec files.
- **Approach:** the app finds `this.<key> = page.…;` assignments in the file.
  The AI returns structured fixes. The app renders each new expression with
  the existing `locator_expr` and replaces only that assignment's right-hand
  side. Every other byte of the file is kept.
- **Placement:** a new page, `pages/4_Heal_Locators.py`.

## Scope

**In scope:** the new page; parsing, patching and diffing in
`core/locator_healing.py`; a new AI call and prompt; tests; docs.

**Out of scope:** healing spec files or assertions; adding locators;
multi-line locator expressions; running Playwright from the app; batch
healing of several files at once.

## Parsing (`core/locator_healing.py`)

`parse_locators(source: str) -> tuple[list[dict], list[int]]`
- A locator is a line matching
  `^(\s*)this\.([A-Za-z_$][\w$]*)\s*=\s*(page\.[^;\n]*);\s*(//.*)?$`.
- Each locator is returned as `{"key", "expression", "line"}`, where `line` is a 0-based index.
- The second value lists the 0-based lines that start `this.<key> = page.` but
  do not match, for example because the expression spans several lines. The
  UI reports them as skipped.
- If a key is assigned twice, only the first assignment counts, and the
  later line is reported as skipped.

Limits: the file must be at most 100,000 bytes and valid UTF-8, the error at
most 20,000 characters, and the snapshot at most 50,000 characters.

## Data model (`core/ai_client.py`)

```python
class LocatorFix(BaseModel):
    key: str                 # must be a key found in the file
    strategy: Literal["role", "label", "placeholder", "text", "test_id", "css"]
    role: str                # ARIA role when strategy == "role", else ""
    value: str
    confident: bool          # True only when the element is in the new snapshot
    reason: str              # e.g. "Button text changed from 'Sign in' to 'Log in'"

class HealingResult(BaseModel):
    verdict: Literal["fixed", "element_missing", "behaviour_changed", "not_a_locator_problem"]
    fixes: list[LocatorFix]
    explanation: str
```

All fields are required. The AI sends empty strings for unused fields.

## Validation

`validate_fixes(fixes: list[dict], locators: list[dict]) -> tuple[list[dict], list[str]]`
returns the kept fixes (each with the rendered `expression` added) and warnings:
- A fix whose `key` is not in the file is dropped with a warning.
- A second fix for the same key is dropped with a warning.
- A role outside `ARIA_ROLES`, or an empty role with `strategy == "role"`,
  falls back to `strategy = "text"` with `confident = False`. An unknown
  role also gets a warning. This is the same rule as
  `core/automation_validate.py`.
- A fix whose rendered expression equals the current expression is dropped
  with a warning ("no change").
- `reason` is reduced to one line for the comment.
- When the current expression has something the fix would drop — a chain
  such as `.nth(2)`, `.first()` or `.filter(...)`, or options other than a
  role's accessible name, such as `{ exact: true }` — the fix is kept but
  flagged (`drops_detail`) with a warning, and its checkbox starts unticked.
  The prompt tells the AI to return no fix when one getBy/locator call is
  not enough.

## Patching

`apply_fixes(source: str, locators: list[dict], fixes: list[dict]) -> str`
- For each fix, it replaces the matched `page.…` expression on the key's line
  with the fix's expression.
- It inserts the comment `// healed: <reason>` directly above that line,
  with the same indentation. When `confident` is false it also inserts
  `// TODO verify locator: not confirmed by the new snapshot`.
- It keeps the file's line ending (CRLF or LF), and whether the file ends
  with a trailing newline.
- Fixes are applied from the bottom of the file up, so the recorded line
  indices stay valid.

`unified_diff(old: str, new: str, file_name: str) -> str` uses `difflib`
with `a/<file>` / `b/<file>` headers.

## AI call

- `AIClient.heal_locators(system_prompt, file_name, locators, error_text, snapshot) -> dict`
  returns `{"healing": HealingResult dict, "usage": {...}}`.
- The new prompt, `prompts/locator_healing_system_prompt.md`, is combined
  with the project config by `build_system_prompt`. Its rules:
  - fix only locators that the error or the snapshot shows are broken;
  - prefer role, then label, then test id, then css;
  - set `confident` only when the element is in the snapshot;
  - never change a locator to make a wrong expected result pass;
  - when the element is gone, use `element_missing`;
  - when the flow or the expected result changed, use `behaviour_changed`;
  - when the error is not about finding an element (timeout on the network,
    assertion on text), use `not_a_locator_problem`.
- The user content wraps its parts in tags:
  - the locators as JSON inside `<locators>`;
  - the error inside `<error>`;
  - the snapshot inside `<page file="…">`.

  All of it is marked as data, never instructions. A closing tag that
  appears inside the pasted content is neutralised (`<\/error`, …), using
  the same helper as the Automation request.
- The call goes through the existing `_call_ai` (non-streaming, `max_tokens=16000`).

## UI (`pages/4_Heal_Locators.py`)

1. Sidebar: the shared API key block. A project config selectbox.
2. Upload `.ts`. The app shows the table of locators it found and a caption
   listing skipped lines. A file that is not UTF-8, is too large, or has no
   locators shows an error.
3. A "Playwright error" text area and a "Current HTML/ARIA snapshot" text
   area. A caption warns that both are sent to Anthropic, so tokens and
   personal data should be removed first.
4. The **Heal locators** button is disabled, with the reasons listed, until
   the file is valid with at least one locator, the error and the snapshot
   are non-empty, and all limits hold.
5. The result shows:
   - the verdict and the explanation, with a prominent warning when the
     verdict is not `fixed`;
   - warnings from validation;
   - one checkbox per fix (checked by default), showing the old expression,
     the new expression and the reason;
   - the diff of the patched file for the checked fixes;
   - a download of the patched file under the original file name;
   - the token cost.

   When no fix is kept: "The AI proposed no locator changes."
6. The result is stored in `st.session_state["healing_result"]` together with
   a signature of file name + content + error + snapshot + project. It is
   cleared when any of them changes.

## Error handling

AI errors use the existing retry and `ValueError` path. Bad fixes are
dropped with warnings, never raised. The input limits are enforced before
any AI call.

## Testing

- `tests/test_locator_healing.py`:
  - parsing covers a renderer-generated file, a hand-edited file (extra
    methods, comments, non-locator lines), multi-line and duplicate
    assignments, and a trailing `//` comment;
  - validation covers an unknown key, a duplicate key, an invalid or empty
    role, and a no-change fix;
  - patching covers the exact lines changed, keeping CRLF and the trailing
    newline, indentation of the comment, hostile strings in `value` and
    `reason`, and several fixes at once;
  - the diff output.
- A round trip: the fixture page object from the Automation golden files is
  patched with a fixture healing result. A golden file pins the output, and
  CI's `automation-smoke` job type-checks it together with the fixture
  project.
- `tests/test_ai_client.py`: `heal_locators` uses `HealingResult`, the tags
  and the closing-tag neutralising; `tests/test_prompt_builder.py` covers
  the prompt.
- `tests/test_heal_page.py` (AppTest):
  - the disabled button and its reasons;
  - the full flow with a mocked AI;
  - unchecking a fix changes the diff and the download;
  - a non-`fixed` verdict shows its warning;
  - a new upload clears the result.
